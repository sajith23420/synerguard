# SynerGuard — Drug Interaction Checker

A full-stack drug–drug interaction checker built for a Management Information
Systems dissertation. Enter the medicines a patient is taking; the system flags
every known interaction, ranks each by clinical severity, and — where curated
evidence exists — recommends a safer alternative. It also surfaces drug–food
interaction notes.

Of the 314,068 interaction pairs in the source data, **183,598 carry no severity
grade at all**. A machine-learning model fills 56,342 of those gaps where it can
do so defensibly, and the interface keeps those estimates visibly apart from
graded data. How that separation is designed — and where the model is refused —
is the substance of the project.

**No database to install, and no Python at runtime.** The backend loads JSON
files straight into memory on startup (~1.3s). Just `npm install` and run.

## Data

Four public datasets have been cleaned and merged, with a fifth layer generated
by the model in `ml/`:

| Source | What it contributes |
|--------|--------------------|
| DDInter | Severity levels (Major / Moderate / Minor) |
| DrugBank 6.0 | Interaction descriptions |
| Curated DDI | Rich clinical detail: mechanism, effect, **safer alternative**, management |
| Drug–Food interactions | Food / supplement warnings per drug |
| `ml/04_export.py` | Severity estimates for pairs the sources left ungraded |

Counts, verified against the data files:

| | Count |
|---|---|
| Drugs | **2,691** |
| Interaction pairs | **314,068** |
| Curated records (full clinical guidance) | **79** |
| ML-predicted severities | **56,342** |
| Drugs with food notes | **1,423** |

Severity in the source data: Moderate 96,691 · **Unknown 183,598** · Major
26,937 · Minor 6,842.

The data lives in `server/src/data/` as newline-delimited JSON:
- `drugs.json` — drug documents (with food interactions)
- `interactions.json` — interaction documents
- `predictions.json` — ML severity estimates, generated by `ml/04_export.py`

## The four tiers

Results carry different grades of evidence. Keeping them apart is the point:

| Tier | Count | How it reaches the user |
|---|---|---|
| **Curated** | 79 | Mechanism, clinical effect, management, safer alternative |
| **Known** | 130,391 | Severity graded by the source datasets |
| **Predicted** | 56,342 | ML estimate, **opt-in**, violet dashed `Predicted · 94%` badge |
| **Unknown** | 127,256 | Left ungraded, with a stated reason where one applies |

Two rules hold the tiers apart, and both are enforced in `store.js`:

1. **The `severity` field is never written to.** A prediction lands in separate
   `predictedSeverity` / `confidence` / `source` fields.
2. **Only records already sitting at `Unknown` are touched**, so an estimate can
   never overwrite — or quietly downgrade — a graded interaction.

Predictions are hidden until the user opts in, and carry an explicit warning
that a predicted "Moderate" may be more serious. Held-out recall for Major is
0.67: roughly one genuinely Major interaction in three is estimated lower, which
is why they supplement the graded tiers rather than replace them.

## Architecture

```
drug-web/
├── server/                  # Express API, JSON in-memory store
│   └── src/
│       ├── data/            # drugs.json, interactions.json, predictions.json
│       ├── store.js         # loads + indexes on startup; attaches predictions
│       ├── routes/api.js    # /stats, /drugs/search, /drugs/resolve, /check
│       └── index.js
├── client/                  # React 19 + Vite frontend
│   └── src/
│       ├── App.jsx          # state, filtering, sorting
│       ├── api.js
│       └── components/
└── ml/                      # severity-prediction investigation (Python)
    ├── features.py          # shared loader + FeatureBuilder
    ├── 01_baseline.py       # how much is predictable, and from what
    ├── 02_experiments.py    # leakage control, unseen drugs, thresholds
    ├── 03_apply.py          # how many gaps can responsibly be filled
    ├── 04_export.py         # writes predictions.json
    └── README.md            # full results and limitations
```

Python is needed **only** to regenerate `predictions.json`. The file is committed
as the artefact of record, so the app runs on Node alone. Delete it and the
server logs `running without the predicted tier` and behaves exactly as it did
before the ML work.

## Setup

### 0. Prerequisites
- Node.js 18+  (that's it — no MongoDB, no database)

### 1. Start the backend
```
cd server
npm install
npm run dev            # API on http://localhost:5000
```
On startup you'll see:
```
Data loaded in 1.3s — 2691 drugs, 314068 interaction pairs, 79 curated, 56342 predicted.
```

Verify: open http://localhost:5000/api/stats — you should see the counts.

### 2. Start the frontend
```
cd client
npm install
npm run dev            # client on http://localhost:5173
```
Vite proxies `/api` to port 5000, so start the server first.

### 3. Regenerating predictions (optional)
Only needed if `interactions.json` changes:
```
cd ml
python 04_export.py    # needs scikit-learn + numpy
```
See `ml/README.md` for results, thresholds and the library versions used.

## API reference

| Method | Endpoint | Purpose |
|--------|----------|---------|
| GET | `/api/stats` | `{ drugs, interactions, richRecords, predicted }` |
| GET | `/api/drugs/search?q=` | Autocomplete → `{ results, fuzzy }`; `fuzzy: true` means the query had no literal match and these are typo-corrections |
| GET | `/api/drugs/resolve?name=` | Is this name known? → `{ input, known, canonical, suggestions }` |
| POST | `/api/check` | Body `{ drugs: [...] }` → interactions, food notes, unscreened drugs, predictions |

`/api/check` returns 400 for fewer than two entries, or any entry that is not a
non-empty string. Unrecognised *names* are not an error — they come back under
`unknown`. Response fields:

| Field | Meaning |
|---|---|
| `totalPairs` / `flagged` | Pairs checked, and how many had a record |
| `counts` | Graded severities only — **never includes estimates** |
| `predictedTotal` / `predictedCounts` | Estimates, tallied separately |
| `recognised` / `unknown` | Names resolved, and names not in the data |
| `unscreenedPairs` | Pairs lost to an unrecognised name |
| `unpredictable` | Unknown pairs with no estimate, each with a reason |

### Unrecognised drug names

A checker fails dangerously if a drug it has never heard of simply contributes
no interactions — the regimen then looks clean when it was never checked. So
names outside the dataset are never silently dropped:

- Typos are caught by bounded Levenshtein matching over normalised names
  (`warfrin` → Warfarin, `asprin` → Aspirin). A candidate must share the first
  letter and clear a similarity floor before it is offered, because a plausible
  wrong suggestion is worse than none here — `panadol` → *Danazol* would be
  actively harmful, so it is suppressed.
- Names with no close match can still be added, and come back in `unknown`.
  `/api/check` reports `recognised`, `unknown` (each with suggestions) and
  `unscreenedPairs`; the UI marks those chips as unscreened and states plainly
  that a clean result does not cover them.
- Brand names (Panadol → Paracetamol) are *not* resolved. Edit distance cannot
  bridge that gap — it needs an alias table, which is not yet built.

### Refusing to guess

The same principle governs the model. Where a pair has no estimate, `/api/check`
says so and gives the reason rather than staying silent, because once *some*
Unknown pairs start showing an estimate the rest begin to read as "checked,
nothing found":

| Reason | Pairs | Meaning |
|---|---|---|
| `insufficient-data` | 77,810 | A drug has fewer than 5 graded interactions, so the model has no usable profile for it |
| `low-confidence` | 49,446 | Both drugs are well covered, but the estimate fell below 0.90 |

The first message names the drug responsible:

> Cannot predict severity: 'Bromazepam' has too little interaction data to
> estimate reliably. Treated as Unknown — please verify manually.

This matters because the model learns per-drug tendencies rather than
transferable pharmacology. With both drugs unseen its macro-F1 falls to 0.338 —
barely above guessing — so refusing is the honest output. See `ml/README.md` §2B.

Example:
```
curl -X POST http://localhost:5000/api/check \
  -H "Content-Type: application/json" \
  -d '{"drugs":["Warfarin","Ibuprofen","Aspirin"]}'
```

## For the dissertation

- **The contribution is the prediction plus its boundary**, not the app. Network
  structure predicts missing severity grades (macro-F1 0.28 → 0.77), but the
  signal is per-drug tendency rather than transferable pharmacology, so it
  collapses for unseen medicines (0.34). Filtering on coverage and confidence
  fills 31% of the gap at 94% agreement; the other 69% keeps declaring itself
  unknown. Full numbers in `ml/README.md`.
- **Two negative findings are worth reporting**, not hiding: the description
  text is nearly worthless as a feature (macro-F1 0.284 → 0.310, barely off the
  floor), and the model cannot generalise to new drugs. Both sharpen the claim.
- **Evaluation**: the untested assumption is that clinicians read an estimate
  *as* an estimate. Two-round survey — (1) need validation before, (2) usability
  after, including whether the predicted tier is correctly understood.
- **Say "agreement", not "accuracy"**: 86% is agreement with DDInter's grading,
  not clinical correctness. Establishing the latter needs clinician review.
- **Limitations to state honestly**: no dose/timing/patient-specific factors,
  curated guidance covers only 79 pairs, source data is public and not
  independently verified, and Major recall of 0.67 means the least safe error is
  the commonest one.
- **On the stack**: React + Express + Node with a JSON data layer. The data is
  already in MongoDB-ready format if a true "MERN" framing is wanted later.

### Maintenance note

`MIN_HISTORY` / `MIN_CONFIDENCE` in `ml/04_export.py` are duplicated as
`MIN_LABELLED_HISTORY` and the export threshold in `server/src/store.js`. They
must be changed together — if they drift, the app will warn about pairs the
export happily predicted. Both files carry comments pointing at the other.
